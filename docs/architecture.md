# 架构

Go 单进程：对话轮询、路由、音频服务和管理接口都在一个进程里，SQLite 持久化，管理页嵌入程序。

## 点歌流程

1. **读取对话**：按“设置 → 听歌识别”的间隔（默认 2 秒，观察模式的音箱慢一倍，安静一阵后放慢，睡眠时段不读）读取小爱音箱最近的 5 条对话，读取失败时退避；小米拒绝读取时整个账号一起等。识别出的点歌和播放控制口令按设备 ID 与请求 ID 去重后入库，其他对话只在内存里计数。启动后的第一次读取只建立水位，不补播之前的口令。
2. **查曲库**：先查飞牛音乐的本地索引；没登录飞牛音乐时，查只读挂载的音乐目录。
3. **查线上**：曲库没有时查酷我、酷狗、咪咕、网易云。歌名、歌手匹配，并探测到完整可播的音频，才作为候选。
4. **接管或交回**：有候选且音箱允许接管，就打断小爱并投放；没有候选则由小爱继续处理。
5. **回读**：分别记录“已下发”“音箱已取流”“已确认播放”和“待确认”。接口返回成功不代表歌已经在放，以取流和状态回读为准。

小米生成对话记录时，小爱可能已经开始回答，所以接管总是先静音再停止。识别后 2 分钟以上才读到的口令标为“延迟到达”，不执行。口令记录保留 180 天。

## 模块

| 包 | 职责 |
| --- | --- |
| `cmd/trackferry` | 读取配置、组装依赖、信号处理与优雅退出 |
| `internal/store` | SQLite（`modernc.org/sqlite`，纯 Go、免 cgo、支持 FTS5），迁移、事务与保留期清理 |
| `internal/xiaomi` | 小米账号会话、对话记录轮询、音箱投放、停止与状态回读；按型号区分投放方式 |
| `internal/intent` | 从识别词解析点歌意图（歌名、歌手），规则实现，可单测 |
| `internal/names` | 歌名、歌手归一化（繁简、括号版本、多歌手） |
| `internal/audio` | FLAC、MP3、MP4、WAV 标签与时长读取，GBK 乱码修复 |
| `internal/feiniu` | 飞牛音乐客户端：登录、证书钉扎、曲目与专辑歌手、封面、歌词、取流 |
| `internal/library` | 同步飞牛音乐或只读扫描目录，内存索引、检索、专辑与歌手浏览 |
| `internal/online` | 在线源适配器接口及酷我、酷狗、咪咕、网易云实现 |
| `internal/cache` | 听过的线上歌：开始播放 20 秒后另行下载完整一份，按容量淘汰最久没听的；同样的请求再来时跳过线上查找 |
| `internal/routing` | 路由决策：曲库 → 酷我 / 酷狗 / 咪咕 / 网易云 → 小爱，结果连同各层候选与耗时存入 `commands.route` |
| `internal/takeover` | 接管闭环：静音、打断小爱、推流、守护窗口、确认与恢复音量；按口令分派 |
| `internal/cast` | 投放：搜索局域网里的 DLNA 和 Chromecast 设备，打开的设备按电视的方式由服务端驱动，掉线重连、换 IP 跟上 |
| `internal/tv` | 电视端的配对凭据与服务身份 |
| `internal/fill` | 曲库缺的封面在后台补，没歌词的歌播放时再找；按歌名、歌手、时长和专辑严格匹配，逐个平台慢慢问 |
| `internal/netcover` | 平台封面落盘缓存，同一张只取一次，取不到的一段时间内不再问 |
| `internal/stream` | 音频 HTTP 服务：短期令牌、Range、取流记录；在线流代理（Range 透传） |
| `internal/api` | 管理 JSON 接口、SSE 事件、健康检查、管理员会话 |
| `internal/auth` | 管理密码哈希、首次初始化码、登录限速 |
| `internal/home` | 给 Home Assistant 的音箱状态：合并播放经过与音箱回读，只推送有意义的变化；没有连接时不查询 |
| `internal/live` | 把正在发生的事实时告诉管理页，只报告不决定 |
| `internal/observe` | 按音箱轮询对话、水位与去重 |
| `internal/relay` | 备选的本机通道 |
| `internal/update` | 去 GitHub 看有没有新版本，下载、核对签名并切换；启动时决定用镜像里的还是已安装的程序 |
| `internal/logx` | 中文日志与醒目的提示框 |
| `internal/privs` | 容器只在启动瞬间是 root，把数据目录交给普通身份后切换过去 |
| `internal/config`、`internal/fscheck` | 配置与目录检查 |
| `internal/webui` | 嵌入的管理页静态资产，客户端路由回退到 index.html |

依赖方向单向：`routing` 依赖 `xiaomi`、`library`、`online`、`audio` 的接口，适配器之间互不依赖。所有外部调用接收 `context`，带连接、响应与总预算。

### 飞牛音乐接入

以普通用户身份调用飞牛音乐的接口（`https://<飞牛>:5667/music/api/v1`，按 1.1.19 核对），权限由飞牛判断，不需要挂载曲库，也不修改 NAS 配置。

- 用户在设置里输入地址、用户名、密码；密码只用于这次登录，不落盘。登录后得到的会话写入 `data/private/feiniu.json`（0600）。
- 自签证书在登录时记住指纹，之后指纹不符即拒绝连接。
- 歌曲由 TrackFerry 带会话向飞牛取流，再以短期令牌转给音箱；音箱放不了的格式在同步时跳过。

### 音箱取流路径

音箱只访问 TrackFerry 的局域网地址 `<public_base_url>/stream/<令牌>.<扩展名>`（扩展名给按后缀选解码器的固件看；`public_base_url` 未设置时接管不会开始），本地歌曲与在线歌曲都由 TrackFerry 提供：

- 飞牛音乐的歌由 TrackFerry 代理取流，透传 Range。
- 未登录飞牛音乐时，本地文件直接流式读取，支持 Range，不整首载入内存。
- 在线歌曲由 TrackFerry 代理上游直链：统一处理防盗链请求头、直链过期重取和 Range 透传，并且每次取流都能关联到执行记录，“音箱已取流”的证据由此而来。
- 令牌为 128 位随机数，是取流唯一的访问控制（音箱不带登录态），目前固定 6 小时过期；只服务 TrackFerry 自己选中的文件，路径不能逃出曲库目录。
- 第一次取流即记为“音箱已取流”，用于判断投放是否生效。

### 配置与私有数据

- 环境变量或 `data/config.yaml`：监听地址、对外音频地址、接管放行、检查更新。见[配置](configuration.md)。
- `data/private/`：小米会话等凭据，权限 0600，只在飞牛本地生成或复制，不进镜像、日志和诊断导出。
- `data/trackferry.db`：执行记录、事件、水位、去重、设备设置、曲库索引。

## 在线源

酷我、酷狗、咪咕、网易云的适配器都在主进程内，代码在 `internal/online`。每个适配器实现 `Search`、`Resolve` 和健康状态，各有并发上限、超时、熔断与退避，互不影响。

- 歌名与歌手归一化后匹配。
- 取链后探测内容类型、时长和可读字节，试听片段不算完整音频。
- 网易云可以扫码登录用户自己的账号：会话只发给 `https://music.163.com`，账号能完整播放的歌按可播处理，和别的来源一样进缓存（设置里附版权提示）。每 12 小时查一次会话，失效后按没登录处理。
- 没有权限的会员歌曲和时长、演唱者不可靠的上传按受限处理，继续查下一个来源。
- 直链过期时重新获取，音频流支持 Range 透传。

## 小米接入

- **登录**：支持米家扫码和账号密码，最终都换取 `micoapi` 的 serviceToken。密码登录遇到图形验证码时，由服务端代取图片；需要身份验证时，用户在小米页面获取验证码后填回管理页。小米密码只以 MD5 形式留在内存，登录结束即清除，最长 10 分钟。同一 IP 连续失败 5 次暂停 15 分钟。
- **凭据**：passToken、serviceToken 等只写入 `data/private/xiaomi.json`（0600，原子替换），不进数据库、日志与接口响应；界面只显示打码的小米 ID。serviceToken 在获取 10 小时后用 passToken 续期，Mina 返回 401 时立即续期重试一次；passToken 被拒时标记“需要重新扫码”，不触发容器重启。
- **音箱列表**：依次尝试 `device_list` 与 `device_list?master=1`，任何一个返回非空就采用并记录用了哪个。同步结果分为：找到音箱、账号下为空、需要重新登录、网络或接口错误。新发现的音箱默认“不接入”；从账号消失的音箱保留设置并标为“已不在账号中”，不删除。
- **管理员**：首次打开要用一次性初始化码（容器日志与 `data/private/setup_code`）设置管理密码，防止局域网里其他人抢先。密码 PBKDF2-SHA256 60 万次；会话 Cookie HttpOnly、SameSite=Strict，库里只存哈希；写操作要求 `X-Requested-With: trackferry` 头；连续 5 次失败限速 15 分钟。忘记密码用 `docker exec trackferry /trackferry reset-admin`。脚本仍可用 `data/private/admin_token` 的 Bearer 令牌。
- **接管闭环**（`internal/takeover`，每台音箱串行，新指令取消旧的）：
  1. 用上次记下的音量直接静音，同时读状态核对；没有记录才先读（读不到就不静音）。原音量先写入 `pending_volume` 表。`devices.hush` 为加强或等小爱说完时，再经米家静音和暂停（OH2P 默认加强），推送前等它落定并解除：LX06 实测会在静音解除后 20 ms 内断开正在放的流，所以不用米家静音，别的型号也不在歌起播后解除；
  2. 与静音同时开始，`pause`、`stop` 并发，连做两次，打断小爱正在说的话和刚排进的播放；
  3. 静音状态下推送我们的流：LX06、OH2P 等走 `player_play_music`（带固定 audio_id，可在状态里认出是不是我们在放），其余型号走 `player_play_url`；
  4. 守护窗口约 8 秒，每 700ms 读一次状态，发现小爱迟到的歌单抢回播放器就再停再推，最多重推 2 次，超过判失败；
  5. 音箱取流且状态确认在放我们的音频后立即恢复音量；只取流未确认时 2.5 秒后也恢复；
  6. 无论成败都恢复音量（重试 3 次），每步耗时写入 `takeover_runs`。进程崩溃后启动时按 `pending_volume` 补恢复音量。
  7. 推送的地址对音箱来说是只有一首的列表，放完会一直循环：已知时长到点、或音箱在首次取流很久之后又从头取流时，若音箱仍在放我们的音频就停止；在放别的或已停就不动。
  结果分为：已确认、已取流未确认、只下发了指令、失败、被新指令取代。音箱页可以手动做接管测试（提示音或曲库随机一首），看各步耗时。设为接管的音箱听到点歌后自动走同一闭环，新口令取消旧的查找。允许接管的音箱由 `TRACKFERRY_TAKEOVER` 指定。歌曲不按时钟停，只由从头再取流触发停止。
- 观察阶段只读，xiaomusic 照常运行。打开某台音箱接管前，先让 xiaomusic 等同类程序退出对该音箱的接管，避免两个进程同时控制。

## 稳定性约束

- 每台设备独立的有界执行队列和指令版本，新指令取消过期的查找与回读；实际投放前再次校验版本和接管开关。已发出的网络请求不假定可撤销。
- 每台设备投放互斥，限制全局与各音源并发，禁止重叠轮询；单台音箱离线不阻塞其他设备。
- 只读操作允许有界退避重试，鉴权失败与限流分别处理；投放结果不确定时先回读，无匹配证据保留“待确认”，禁止自动补发。
- 投放意图先落库；重启后中断任务标为“待核实”，不自动重放。恢复后仍遵守启动水位和设备观察默认值。
- SQLite：WAL、busy timeout、单写连接；限制记录保留期和磁盘占用。持久化失败时暂停新的接管投放并报告。
- 曲库扫描使用有界工作池，增量、可取消；音频流、事件订阅和 HTTP 连接均有上限。暴露轮询延迟、执行耗时、队列深度、内存与错误率。
- 健康检查区分存活、初始化和外部依赖故障；音源或小米接口不可用不导致容器重启循环。

## 部署

多阶段 Dockerfile 产出静态二进制，运行镜像从 scratch 起，非 root、只读。默认 host 网络，一个服务。备选的桥接方案见 `compose.bridge.yaml`。发版镜像由 `scripts/publish.sh` 交叉编译。

## 管理页

管理页背景是 WebGL2 水面，颜色取自当前歌曲封面；没有封面时按歌名生成图案。流转页按记录的时间播放一次点歌的经过。尊重系统的减少动态效果设置，不支持 WebGL2 时使用静态背景。

- **此刻**（首页）：最近一次或正在放的点歌、歌词、四站结果；按天的记录；试一句看谁来放（不出声）。
- **流转**：一句话从听到、查找、接管到出声的全过程，实时跟随（SSE `/api/live`），也可回放；数据只来自后端记录的事件。
- **怎么说**：能听懂的说法与示例。
- **曲库**：搜索、最近添加、专辑、歌手，单曲可送到已接入的音箱。
- **音箱**：不接入 / 观察 / 接管，未放行的接管上锁；接管测试。
- **设置**：飞牛音乐、小米账号、线上音源、管理密码。首次使用仍是三步引导。

## 飞牛探测

依次问本机、已知地址和网关；都没有应答时才看同一网段。只读一个公开页面，不带凭据。host 网络下直接连 `127.0.0.1:5667`。备选的 `relay` 容器把共享卷里的 Unix 套接字转到同一地址，供桥接容器使用；主容器只在套接字存在时使用它，证书校验仍是端到端。

## 同名歌曲

同名歌有多位歌手时，依次按收藏、线上对原唱的意见、匹配分、曲库里歌曲最多的歌手选一首播放；有收藏或曲库里某位歌手明显占多时不问线上。问线上只看原唱是谁，不取歌，会员歌也算意见（`Layer.Opinion`），其余歌手写入 `route.others`。两个平台意见不同时按顺序尝试。

## 打断与续播

音箱（LX06 实测）不回报自推音频的进度，所以进度由服务端自己计时。播放中每 2.5 秒读一次状态，有人说话或刚停下时每 0.9 秒一次，停着超过 2 分钟后每 10 秒一次，放完、停下或被取代后不再读。有人和小爱闲聊后音箱停了，等小爱按答复长度估算说完，从断点前 1.5 秒重新推送（MP3、FLAC 从中间切，其他格式从头）。听者要求暂停、停止、安静，或小爱去放别的音频时不续播；没人说话而停下视为手动暂停。`Player.Elapsed` 与 `Phase` 经 `/api/live` 给出，页面的歌词与“正在播放”只认它。从曲库推送的歌记为 `push`，`takeover_runs.song` 保存歌曲。

## 连播

`routing.list` 现读飞牛音乐的收藏或歌单（读不到收藏时用上次同步的标记），按 GUID 对到曲库并打乱，第一首照常接管。`takeover.queue` 每台音箱一个，只在内存里；一首的 `Request.Ended` 报告放完、没放出来还是被停下，放完才推下一首（`Request.Follows`：不静音，也不再停小爱），记为 `push`，`song.list` 写着连播的名字。歌手连播、从页面推的列表、“接着随机放”走同一个队列，`queue.until` 到了（默认 3 小时）就不再推下一首。新的点歌、按停止或说停止都丢弃队列；“下一首”“上一首”在有队列时由我们换，否则归小爱。

## 接着说换版本

点过一首歌（含推送、没找到的）15 分钟内，“放某某的”“换成某某的版本”“不是这个，放某某的”指上一首歌由这位歌手唱的版本：先按曲库里唱过它的歌手对，允许听错一个字；再找真以“的”结尾的歌名；再去线上找。“换个版本”换成曲库里还没放过的另一位歌手。没有上一首时，“放某某的”等于听这位歌手；“换…”类的话不入库，按闲聊处理。

## 播放端与歌词时间

手机或电脑的「本机」播放使用浏览器音频时钟。进度和逐行歌词共用同一个读数；拖动目标只供预览，等音频定位完成后才更新当前位置。歌词内容和每曲校准由服务端提供，本机的待播队列保存在当前浏览器。

小爱音箱以音箱的取流和状态回读为凭据。它们可以说明音箱是否开始播放，通常不能报告实际播放到该音频的哪个位置，所以小爱端歌词和进度仍是估算。远程定位关联当前播放记录，客户端取消或换歌后，尚未执行的定位作废。

原生 Android TV 端复用曲库、音频与歌词接口，使用电视自己的媒体时钟播放和显示歌词。设备配对、手机遥控和跨端接力分阶段实施。见 [TrackFerry TV 实施方案](android-tv.md)。
